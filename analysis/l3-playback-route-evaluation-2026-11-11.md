# 播放内核两条路线评估：继续复用 vs 逆向重写（2026-11-11）

> **性质**：技术尽调 / 决策支持报告，**非正式批次、不推进技术断点、零生产代码改动**。
> 全部量化基线来自本仓库实证（`docs/11`/`13`/`05`/`12`、18 so、反编译产物、
> F3/F4/A3 证据 JSON）；业界对照引用 Android 官方 Media3 文档。
> 工期是**估算区间 + 置信度**，不是承诺；不作法律结论。
> 当前状态：**F4 仍 BLOCKED**，真机取证已于 `§61.75` 完结。

## 0. 结论速览

| 维度 | A. 继续复用竞品内核 | B1. 只重写 Java/JNI 胶水 | B2. 换开源播放内核（Media3 + FFmpeg 扩展） | B3. 全栈重写（含音效 DSP/AI） |
|---|---|---|---|---|
| 工期（本项目 AI 辅助吞吐） | **1~3 周**（若「绕过取流」成立）；若必须改 native → **1~2 个月且成败不确定** | 2~4 周 | **6~12 周** | 4~8 个月 |
| 工期（1 人全职人工，参考口径） | 3~8 周 / 改 native 不可控 | 6~12 周 | **3~6 个月** | 9~18 个月 |
| 复杂度（1~5，5 最高） | **2**（局部修复）；改 native = 5 | 3 | **4** | 5 |
| 短期功能稳定性 | **4**（二进制成熟，F3 11/14 格 PASS） | 3（so 不变，F4 不变） | 2（新栈重踩坑，格式覆盖全量重跑） | 1 |
| 长期可修复性 | **1**（黑盒、无源码、F4 已证无 Java 侧解） | 2 | **5**（有源码、可调试、F4 类问题自然消失） | 5 |
| 沉没成本保留 | **全部保留** | 大部分保留 | **大部分作废**（F3 14 格 / A3 / 长稳全量重跑） | 几乎全废 |
| 合规/演进 | GPL FFmpeg + 私有 so，D-146 自用可控、公开发布受阻 | 同 A | **可解 R7**（换 LGPL/开源栈） | 可解 |

**一句话建议**：给 A 一个**有时间盒的验证**（3~5 天 AI 辅助 / 2~3 周人工），只验一件事：
「绕过取流」能否让 `Write start play` 出现、F4 主判据通过。**成立就继续 A；不成立立即转 B2**。
不要做 B1（最没意义：保留了黑盒 so，F4 一点没变），个人自用项目不要做 B3。

## 1. 评估口径与假设

### 1.1 两条路线的准确定义

- **A 继续复用**：保留 18 个竞品 so、`libffmpeg.so`、212 个 JNI 导出、
  已照搬的 Java SDK 层与 `engine-legacy` 舱；只修 F4 取流/缓存层的问题，
  继续走 `§61.77` 之后的 F4 验收 → F5 → P2→P3→P4。
- **B 逆向并重新实现**：**必须拆三层**，混在一起估会差一个数量级：
  - **B1**：只重写 Java/JNI 胶水层（自研 `IMusicEngine` 实现），**仍调用竞品 so**。
  - **B2**：放弃 `libncmplayerengine` / `libNMCommonCache` / `libncmaudioplayer`，
    用 Media3/ExoPlayer + 按需裁剪的 FFmpeg 软解扩展 + 自研缓存/Range 重建播放内核
    （即架构里预留的 `:engine-opensource` 逃生舱，`docs/02 §0 A4`）。
  - **B3**：B2 之上再自研完整音效 DSP 链、AI 音效、空间音频、Hi-Res/USB 独占。

### 1.2 工期口径

| 口径 | 说明 |
|---|---|
| **本项目 AI 辅助吞吐** | 实证：2026-11-05 首批 → 11-11 共 **7 天 / 104 个交付批次**，产出 20 模块、生产 Kotlin **21,516 行**、430 测试 / 47 套件、18 so 引入、F3 14 格真机矩阵、三轮 60s 真机观测。**这是 AI 辅助下的高频交付，不能线性外推到人工排期**。 |
| **1 人全职人工（参考）** | 常规工程排期口径，含设计/实现/真机回归/文档；按本项目已实证的功能面折算，约为 AI 辅助口径的 3~5 倍。 |

> 两个口径都**不含** F5 之后 P2/P3/P4 的 UI 与模块补齐（`docs/17 §4`），
> 那部分与播放内核选型正交，另算。

### 1.3 「稳定性」拆成四维（否则无法比）

1. **功能稳定性**：能否稳定播放、格式覆盖、有无 `-103`/无出声。
2. **可修复性**：出问题时能否定位、能否改、改完能否回归。
3. **环境稳定性**：Android / MIUI 版本、后台态、ABI、设备碎片。
4. **演进/供应稳定性**：能否升级、依赖是否可控、权利状态。

## 3. 路线 A：继续复用竞品播放内核

### 3.1 剩余工作拆解

| 工作项 | 内容 | 估算（AI 辅助） | 估算（人工） |
|---|---|---|---|
| A0 接线回滚拍板 + 守护同步 | `§61.69` `SetLoggerCallback` 回滚，同步调整 §61.69/71/72/73/74/75 守护 | 0.5 天 | 1~2 天 |
| A1 **绕过取流**（推荐先试） | 不动 native，改取流/缓存路径让数据不经过 `NMCommonCache` 的代次门控；需设计 + 注入 + 真机回归 | **3~7 天** | 2~4 周 |
| A2 改 native（备选） | 对 `0x10798` / `0xc728` / `0x12dc8` 打二进制补丁或 hook。**so 已 strip、无 `.symtab`、无源码、虚表槽类型运行时决定**（`§61.56` 边界） | **2~4 周，成败不确定** | 不可控 |
| A3 F4 验收 + F5 | 按 `§61.74/§61.75` 多信号判据复跑；A3 全绿后 ABI 回填 + 冻结舱 | 3~7 天 | 2~3 周 |
| A4 剩余 | F3 的 7 种 NO_SAMPLE 需样本/换源；T-V USB 项需物理在场 | 不定（依赖用户） | 不定 |
| **合计（A1 成立）** | | **1~3 周** | **3~8 周** |
| **合计（需 A2）** | | **1~2 个月，且可能无解** | 不可控 |

### 3.2 复杂度：2/5（局部），但含一个 5/5 的悬崖

- 上层全部现成：`IMusicEngine` 门面、19 模块接线、F3 矩阵、真机注入通道、
  41 个诊断工具、守护链都在。
- 但 `§61.59` 已裁定「**native 级缺陷无法 Java 侧修复**」；§61.77 的三处锚点
  全在 native 缓存层。**A 的全部风险压缩在 A1 能否成立这一个点上**。

### 3.3 稳定性：四维

| 维度 | 评分 | 依据 |
|---|---|---|
| 功能稳定性 | **4/5** | 二进制是竞品线上验证过的：F3 11/14 格 PASS、冷/暖轮 `Open codec for aac` + `mDuration 2933` 都通；问题集中在 REMOTE 取流这一条 |
| 可修复性 | **1/5** | 18 so 无源码、已 strip；41 个工具 + 28 个 F4 批次静态定位到指令级仍未能修复；F4 主判据无一 PASS |
| 环境稳定性 | **3/5** | A3 G09 PARTIAL（MIUI 后台态抑制 START_STICKY）非代码缺陷；ABI 仅 arm64-v8a，Android 版本升级无适配权 |
| 演进/供应 | **1/5** | so 无法升级、GPL FFmpeg + 竞品私有库权利状态限制公开发布（R7）、`assets-mapping.csv` 61 行 `replaced=false` |

### 3.4 A 的死局条件（必须写清楚）

若 A1「绕过取流」在真机上仍不能让 `Write start play` 出现 / `-103` 消失，
则 A 只剩 A2（二进制补丁）这条**无源码、无符号、无回归基线**的路。
以本项目已投入的 41 工具 / 72 证据仍未修掉 F4 的事实判断，
**继续投入 A 的边际收益很低**。

## 4. 路线 B：逆向并重新实现（分层）

### 4.0 逆向本身的成本（两条路线共有的前置）

- 已有成果：§61.50~§61.77 的静态反汇编把 F4 因果链定位到指令级
  （`0x10798` → `commit` 冻结 → `result:-2` → -103 → 播放侧门控），
  41 工具 / 72 证据 / 38 logcat。**这证明「逆向定位」做得动，但也证明
  它不等于「能修」**。
- 静态证据的硬边界（`§61.56`）：虚表槽类型由运行时决定，
  静态反汇编不是 100% C++ 类型证明；结构体布局、回调时序、锁与线程模型
  需要动态插桩才能确认。
- Java 侧闭包 **135,954 类 / 76.3% / 深度 21 层**（`docs/11`）——
  说明「照搬 SDK 子树」不成立，重写时**必须按接口契约重新设计**，
  而不是逐类翻译。

### 4.1 B1：只重写 Java/JNI 胶水（保留竞品 so）

| 项 | 评估 |
|---|---|
| 范围 | 用自研 `IMusicEngine` 实现替换照搬的 Java SDK 层；212 个 JNI 导出保持原样调用；18 so 不动 |
| 工期 | AI 辅助 **2~4 周**；人工 **6~12 周** |
| 复杂度 | **3/5**（按 12 个精确 JNI 类 + 4 个包族重写；但闭包裁剪判据已不通过，需重新设计边界） |
| 稳定性 | 短期 **3/5**（so 行为不变，仍有 F4）；长期 **2/5**（黑盒依旧，只是胶水换成自研） |
| **收益** | 代码自主、去掉 `com.netease.*` 类名依赖、R8/C2 问题缓解 |
| **致命问题** | **F4 一点没变**（根因在 `NMCommonCache` native 层）。投入 2~4 周只换来「胶水自研」，播放仍不出声 |

> **结论：不建议单独做 B1**。它是「高投入、零解决主断点」的中间态。

### 4.2 B2：换开源播放内核（推荐的可选路线）

| 项 | 评估 |
|---|---|
| 范围 | 移除 `libncmplayerengine` / `libNMCommonCache` / `libncmaudioplayer` 等私有 so；用 Media3/ExoPlayer（平台 `MediaCodec` 硬解优先）+ 手动构建的 FFmpeg 软解扩展（按需裁剪 decoder）+ 自研 Range/缓存层重建；上层 `IMusicEngine` 门面不变 |
| 工期 | AI 辅助 **6~12 周**；人工 **3~6 个月**（置信度：中） |
| 复杂度 | **4/5** |
| 短期稳定性 | **2/5**：F3 14 格要全量重跑、7 种 NO_SAMPLE 需重新覆盖、gapless/seek/ENDED/ReplayGain 全部自研、`Write start play` 类门控问题会换成新栈的新问题 |
| 长期稳定性 | **5/5**：全链路有源码可调试可修；**F4 类问题随 `NMCommonCache` 一起消失**（这是 B2 最大收益）；可升级、可解 R7（换 LGPL/开源栈） |
| 环境稳定性 | **4/5**：Media3 由 Google 维护、覆盖 Android 版本与设备碎片；后台态/MediaSession 可按官方实践重做，有机会解决 G09 PARTIAL |
| 主要回退 | **音效能力大幅缩水**：103 个音效 JNI / 22 EQ 预设 / 10 混响 / 19 NCAE / MNN AI 音效 / 空间音频 / Hi-Res USB 独占基本归零，只能退化到系统 `AudioEffect` 基础 EQ |
| 沉没成本 | F3 14 格真机矩阵、A3 G01~G09、20 分钟长稳、F4 三轮取证**全部需要重跑**；41 个 `l3_f4_*` 工具中大部分变成历史档案 |

**B2 工期拆解（AI 辅助口径）**

| 阶段 | 估算 |
|---|---|
| Media3 接入 + `IMusicEngine` 新实现 + 门面回归 | 1~2 周 |
| 格式覆盖（F3 14 格 + 7 NO_SAMPLE，FFmpeg 扩展交叉编译/裁剪） | 2~3 周 |
| 缓存 / Range / 网络源注入 / 代理 / 离线闸门接线 | 1~2 周 |
| gapless / seek / 时长 / ENDED / 自动进曲 / ReplayGain | 1~2 周 |
| F3 14 格 + F4 多信号判据 + A3 G01~G09 + 20 分钟长稳全量回归 | 1~3 周 |
| 合计 | **6~12 周** |

### 4.3 B3：全栈重写（含音效 DSP / AI 音效）

| 项 | 评估 |
|---|---|
| 范围 | B2 + 自研 PCM 域效果链（103 个效果接口量级）、10 段/参量/动态 EQ、多段压缩、混响、FIR 卷积、空间音频、响度归一化、NN 推理音效、Hi-Res / DSD / USB 独占 |
| 工期 | AI 辅助 **4~8 个月**；人工 **9~18 个月**（置信度：低，依赖 DSP/音频算法专业能力） |
| 复杂度 | **5/5** |
| 稳定性 | 短期 **1/5**；长期取决于投入是否到位，个人项目很难达到竞品成熟度 |
| 结论 | **不建议**：D-146 是个人自用 / 侧载、V0.1 产品文档明确「均衡器/音效不在范围」（`docs/01 §6`），投入产出比极低 |

### 4.4 业界对照

Android 官方《Media3 ExoPlayer 支持的格式》：**默认使用平台解码器**，
FFmpeg/FLAC/Opus 等软解扩展「必须手动构建」「可选择构建时包含哪些解码器」。
这正是 B2 的标准路径 —— 不是从零写解码器，而是**平台硬解 + 按需软解扩展**，
把工程量集中在缓存/会话/音效接线而非 codec 本身。
（来源：https://developer.android.com/media/media3/exoplayer/supported-formats?hl=zh-cn ）

## 5. 三维度对比矩阵（评分 1~5，5 最好）

| 维度 | A 复用 | B1 胶水 | B2 换内核 | B3 全栈 |
|---|---|---|---|---|
| 工期（越短越好） | **5**（条件成立）/ 1（需改 native） | 3 | **2** | 1 |
| 复杂度（越低越好） | **4** / 1 | 3 | 2 | 1 |
| 短期功能稳定性 | **4** | 3 | 2 | 1 |
| 长期可修复性 | 1 | 2 | **5** | 5 |
| 环境稳定性 | 3 | 3 | **4** | 4 |
| 演进/供应 | 1 | 2 | **5** | 5 |
| 音效能力保持 | **5** | **5** | 2 | 5 |
| 沉没成本保留 | **5** | 4 | 2 | 1 |

两者不是同一时间尺度上的优劣，而是**用短期成本换长期可控性**的取舍。

## 6. 决策建议

### 6.1 建议的时间盒（避免无限投入 A）

```
第 1 步（3~5 天 AI 辅助 / 2~3 周人工）：只做 A0 + A1
  判据：真机上 `Write start play` 出现、本 app AudioTrack state:started、
        自动进曲 3 首无 -103（§61.75 多信号判据）
  ├─ 通过 → 继续 A：F4 验收 → F5 → P2→P3→P4（预计再 1~2 周）
  └─ 不通过 → 停止 A，转 B2（不要转 A2 二进制补丁）
```

### 6.2 转 B2 时必须同时接受的四件事

1. **音效降级**：从 103 JNI / 22 EQ / 10 混响 / 19 NCAE / MNN 退到基础 EQ，
   或明确列为 P4 长期挂账。
2. **全量回归**：F3 14 格 + F4 多信号 + A3 G01~G09 + 20 分钟长稳重跑，
   现有 F4 取证档案转为历史证据。
3. **格式覆盖重做**：7 种 NO_SAMPLE 仍需样本或换源；FFmpeg 扩展要自己交叉编译。
4. **权利状态改善但需确认**：移除私有 so 与 GPL FFmpeg 后 R7 基本解除，
   但 LGPL 重编与编解码授权仍需单独确认（不作法律结论）。

### 6.3 按用户目标给的建议

| 目标 | 建议 |
|---|---|
| 只想让这个自用 App 能播（D-146） | **A + 时间盒**。3~5 天验证「绕过取流」，大概率是成本最低的解 |
| 想长期可维护、能自己修 bug | **B2**，接受 6~12 周与音效降级 |
| 想公开发布 / 商业化 | 必须 B2 起步（R7），外加素材替换（61 行 `replaced=false`）与法务评估 |
| 想 1:1 复刻竞品音效 | B3，个人项目不建议 |
| 只想代码自主、不想换二进制 | B1，但**不解决 F4**，不建议单独做 |

### 6.4 一个容易忽略的判断

**F4 的性质是「native 缓存层缺陷」，不是「解码器缺陷」**（§61.77）。
因此：
- 继续复用 = 带着一个自己修不了的缺陷往前走；
- 换内核 = 直接把缺陷所在的整层删掉。
