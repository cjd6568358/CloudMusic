## 一、结论先行

「卡爆、无法正常听」**不是带宽、不是 CPU、不是缓存 key**，是 **APE 帧对齐契约写错**：
`ApeExtractor` 少了 ffmpeg `libavformat/ape.c` 的三行对齐逻辑，导致每一个包都错位 1~3 字节，
解码器绝大多数帧解不出来，播放位置以 1.5~3.5 倍速虚跳。

| 观测项 | 修复前 | 修复后（同 APK 安装后采样） |
|---|---|---|
| `Error decoding frame` | 2 分钟 **729 次** | **0** |
| `packet size is not a multiple of 4` | **311 次** | **0** |
| 位置推进比 | 10.16s 墙钟 → 20~35s（1.5~3.5×） | 30.0s 墙钟 → 30.4s（**1.01×**） |
| BUFFERING / prepare 次数 | 6 次 / 6 次 | 1 次 / 1 次 |
| 缓存吞吐 | 10s +94MB（≈9.4MB/s） | 同（带宽不是瓶颈） |

## 二、根因（一手证据链）

### 2.1 排除项

- **带宽**：播放中 10 秒缓存增长 94MB ≈ 9.4MB/s；Wi-Fi 链路 2401Mbps、RSSI −37dBm。
- **算力**：`top -H -p <pid>` 播放线程 CPU 0.0%，进程无 CPU 热点。
- **缓存 key**：key 已收敛为 `b2file:<sha256(storageId|path)>`，分轨共享（§61.318 已验证）。

### 2.2 真正的错误

ffmpeg `ape.c` 的帧表构造（`ape_read_header`）：

```c
ape->frames[i].skip = (ape->frames[i].pos - ape->frames[0].pos) & 3;
...
if (skip) { pos -= skip; size += skip; }
size = (size + 3) & ~3;
```

解码器 `apedec.c` 收到包后：`buf_size = avpkt->size & ~3`（**截断到 4 的倍数**），
bswap，然后 `nblocks = BE32(buf)`、`offset = BE32(buf+4)`、`s->ptr += offset`。

旧实现：`writeLeU32(prefix, 4, 0)`（skip 恒 0）+ `size = raw[i+1] - raw[i]`（未 align4）。
后果：
1. 包长非 4 的倍数 → 解码器截断 1~3 字节 → 帧尾熵数据缺失；
2. `offset = 0` → 解码起点落在填充字节上，比特流错位；
3. 解码失败 → 该帧无声，下一帧时间戳跳进 → 位置虚跳、听感断断续续。

### 2.3 文件实测（CDImage.ape，v3990）

```
descLen=52 hdrLen=24 seekLen=6108 wavLen=0 audioLen=304,212,956
blocksPerFrame=73728  totalFrames=1526  firstframe=6184
seek 起点非 4B 对齐：1130 / 1500
帧长非 4 的倍数：  1127 / 1499
skip 分布样例：0,1,2,3,3,3,3,1
```

### 2.4 为什么没被测出来

- `ApeExtractorTest` 原 5 条用例断言的是**存在性**（`samples > 0`、时间戳单调、前缀 LE、
  无 seek 死循环），没有一条断言**字节契约等价**。
- 对照组 `f3_ape.ape` 本身就有大量非对齐帧，只要一句 `offsets.all { it % 4 == 0 }` 就会当场失败。
- 更糟的是 guard §61.149 把**错误结论**写成了判据：
  「必须 `writeLeU32(prefix, 4, 0)`」——把 bug 锁死了，正确修复反而被判回归。

## 三、修复

`ApeExtractor.kt`：

1. `readHeader`：预计算 `frameSkips[i] = (raw[i]-raw[0]) & 3`、`frames[i] = raw[i]-skip`、
   `frameSizes[i] = align4(raw[i+1]-raw[i]+skip_i)`（末帧 `(fileEnd-wavTail) & ~3`）；
   `frameOffsets` 快照改到对齐之后。
2. `readFrames`：包长用 `frameSizes`，前缀第二字写 `frameSkips[i]`。
3. 对齐补齐使相邻包重叠 **0 或 4 字节**（`align4` 向上取整）。为不回退取流
   （§61.107：`RESULT_SEEK` 会让 Media3 重开 DataSource），改为自读缓冲 +
   `carry` 结转，期望流位置 = `pos + carry.size`，顺序推进仍走 `skipFully`。

顺带修：
- `CueEnvelope.displayDuration`：末轨 `cueEnd=0` 原样返回整文件时长（73:45）→ 仅此情形用
  `base - cueStart` 兜底（→ 4:17），`end` 超界仍保持 §61.226 原样。
- `CloudMusicApp`：播放页是覆盖层、搜索框仍在组合内并保持焦点 → 进播放页时
  `clearFocus + hide IME`，否则键盘盖住播放控制区。

## 五、回答「是不是架构根本上就有问题」

分层（engine-api 门面 / 端口 / 组合根）没有问题，两处真架构缺陷（缓存 key、队列点查）已修。
出问题的是**正确性验证层**，具体三个结构性缺口：

1. **手写容器解析器没有差分黄金样本测试**（APE / ASF / WavPack / AIFF 四个）。
   仓库里有完整 ffmpeg 源码，却没有把参考实现做成可执行判据——只能靠人读源码 + 推理，
   推理错一次就是一次真机故障。**这是本批的直接教训。**
2. **guard 以字符串存在性为主**（273 条里大部分是 `if "xxx" not in src`）。
   它防「改回去」，不防「本来就错」，甚至会把错误结论焊死（§61.149 就是）。
3. **文档体量超过代码**（docs/12 已 1.8 万行）。维护账本的成本挤掉了验证成本。

建议（按性价比排序）：

| 优先级 | 动作 | 收益 |
|---|---|---|
| P0 | 给四个 extractor 建「参考 demuxer 输出 → JSON → 单测逐帧比对」的黄金样本测试 | 这类 bug 永不再漏 |
| P1 | guard 只保留少量行为级不变量，删除纯字符串项 | 减少假安全 |
| P2 | docs/12 只留决策 + 判据，过程叙述迁出 | 释放维护成本 |

## 六、UI / 交互评审（设计师视角，按严重度）

截图：搜索结果页（含 IME）、输入法态、播放页、首页、音乐库。

### P0（影响使用）

1. **键盘泄漏到播放页**（已修）：从搜索进播放页，输入法盖住进度条与传输键。
2. **末轨时长错**（已修）：73:45 而非 4:17，进度条几乎不动，像卡死。

### P1（观感/一致性）

3. **双主色打架**：`IconRed #E54545` 用在 21 处（选中态、按钮、光标、搜索 FAB、黑胶标签），
   `BrandOrange #FD7423` 只在音乐库出现 1 次。同一屏里红与橙并存，品牌记忆点被稀释。
   建议：主操作/选中统一橙，红只留给「删除/错误/收藏心形」。
4. **`⌕` 字形像加载环**：搜索框左侧用 14sp 文字字形，渲染出来是一个小圆圈，
   与 loading 指示器同形。应有正式 search 图标。
5. **搜索候选是一屏「别名垃圾」**：`刘若英 / 劉若英 / "刘若英` 三个变体并列，
   没有去重与规范化（繁体/引号），看起来像脏数据外泄。

### P2（细节）

6. 底部导航图标风格混用（实心房子 / 线框音符 / 红色圆底放大镜 / 笑脸），无文字标签，
   「笑脸」语义不明。
7. 播放页副控制行 5 个 12dp 图标（⊙ 💡 ↻ ⓘ ⋯）低对比、语义模糊；黑胶唱臂的支点是一个
   悬浮圆点，像误画。
8. CUE 分轨无封面（`cover_ref` 为空），播放页只能退回黑胶占位，背景取色也无从谈起。
9. 结果行没有「正在播放」标记，列表里看不出哪首在响。

### 一句话评价

骨架（飞牛深色卡片 + 胶囊 tab）是对的，但**细节没收敛**：两套主色、两套图标语言、
三个层级的字号对比不足；搜索页是当前最弱的一屏（IME 态、字形、热词质量三处都掉分）。
