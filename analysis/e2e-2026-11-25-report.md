## G-6 根因（已 A/B 反证）

- A-1（§61.325）把底栏让位钉成 `Modifier.windowInsetsPadding(WindowInsets.ime.exclude(WindowInsets.navigationBars))`，
  并注明「ime inset 已含导航栏高度，不减会多留一条导航栏空档」。
- 真机实测：MIUI 三键导航（底部 insets 165px），键盘弹起时底栏上移 855px（2915→2124），但键盘上沿在 y=2015，
  底栏底部 2124 ⇒ 仍被切 109px。说明 exclude 掉的 navigationBars 恰好就是缺的这段：
  本机的 IME inset 是**净键盘高度**（不含导航栏），再 exclude 导航栏 = 重复扣减 ⇒ 让位不足一条导航栏。
- 修法候选：底栏让位改回 `WindowInsets.ime`（不 exclude），同时 `FnCapsuleBar` 自带 `navigationBarsPadding()`
  保留（键盘收起时仍补导航栏；键盘弹起时三键导航被 IME 顶掉、该 inset 归零，自适应）。
- A/B：把 `exclude(navigationBars)` 改回 `ime` 重构建装机，看红圆是否完整贴在键盘上沿且收起后回原位。

## §61.357 二次修正（2026-11-25 10:06，用户一手否定「推高」方案）

**用户一手**：「搜索页为什么 tab 和播放条跟着键盘推高了？」

§61.356 的做法是把整条底栏上移到键盘上沿（tab 1777~1959 贴住 y=2015）。真机观感 =
「tab 和播放条浮在键盘上方」——方案被用户当场否定。**让位方向错了**：不是把底栏推上去，
而是键盘弹起时底栏让位消失。

**改法**
- `bottomBar`：`if (!WindowInsets.isImeVisible) { Column { MiniPlayer; FnCapsuleBar } }`
  ⇒ 键盘弹起时 bottomBar 高度 0，Scaffold 不再为底栏留白。
- 内容区：`.padding(padding).consumeWindowInsets(padding).displayCutoutPadding().imePadding()`
  ⇒ 先把 Scaffold padding 登记为「已消费」，imePadding 才不会把 navigationBars（165px）
  再补一遍（多补就是一条导航栏高的黑带）。

**真机实测（10:12，Redmi K60 / 1440x3200 / 三键导航 bottom 165px）**
- 弹键盘：uiautomator 里 `首页/音乐库/搜索/更多` 四个 tab 节点全部消失、`text="曾经"` 消失；
  `18-small.png`：键盘贴底、热词直接到键盘上沿，无浮空底栏、无「底栏厚度的黑带」。
- 收键盘：tab 回 `[356,2797][538,2915]`、迷你条「曾经」回 `[259,2524][362,2608]`，分毫不动。
- 键盘顶边 y=2015 实测 (237,239,242) 浅灰线 = MIUI 输入法自带顶边，**不是 app UI**
  （排查「白色透明线」时一并量到）。

**判据**：§61.262/§61.325 升级（正钉 `isImeVisible` 让位 + 内容 `.imePadding()`；
反禁 `exclude(navigationBars)` / `windowInsetsPadding(WindowInsets.ime)` 推高回潮 /
搜索页内重复让位）；§61.356 退化为真机证据链（报告锚点 + 禁 exclude）；新增 §61.357
（consumeWindowInsets 防导航栏双计）。guard 304→305，A/B 4 条全部 FAIL 后逐字节恢复：
A 去掉 isImeVisible、B 底栏推高回潮、C 去掉 consumeWindowInsets、D 搜索页重复 imePadding。

**「白色透明线」：我此前判读错了**。按「找 >100 的亮行」去扫，胶囊内部确实没有亮线，
于是误判成缩略图错觉。用户发来 10:09 原图（1440x3200）后按「相对周围 +6~8」重扫：

- 胶囊顶边 `(43,43,45)` → 中部 `(33,33,36)` 是**单调衰减的渐变**，而 4 个 52dp tab
  内容区在 y=1879~1904 保持 `(40~43)` ⇒ 中心高度浮出一条 +8 的亮带，肉眼即「白色透明线」。
- 根因：`FnCapsuleBar` 的修饰符顺序是 `clip → background → shadow`，**shadow 在
  background 之后（内层）**，Compose 为内容建 graphics layer 并把 8dp elevation 阴影
  画进胶囊内部；layer 边界正好落在 4 个 tab 的内容区，于是内部亮、外面暗。
- 修法：删掉 `.shadow(8.dp, RoundedCornerShape(28.dp))`（深色底上黑影本就不可见，
  属于零视觉损失的减法）。判据 §61.358：FnCapsuleBar 体内禁 `.shadow(`，且盒模型
  四件套（clip/background/padding/圆角）在位；guard 305→306，A/B 注回 shadow → FAIL。
- 教训：亮度判据不能只钉绝对值（>100）。深色 UI 的 banding 是**相对差**（+6~8/255），
  必须扫「同列相邻 y 的差值」而不是「是否达到某个亮度阈值」。
