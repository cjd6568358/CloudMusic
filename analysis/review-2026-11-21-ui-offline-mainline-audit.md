## 1. 复核结论（先给判定）

**判定：功能与架构主线未偏离（11-17 结论在功能侧继续成立）；但「用户体验主线」——UI 样式 / 交互设计 / 离线显示——实质偏离成立，且自 §61.261（2026-11-20 用户更正「其余所有页面统一飞牛」）起连续 9 批零推进。**

偏离的具体形态不是「什么都没做」，而是**结构性错配**：

- **做完的**：V0.2/V0.3 全部功能（SFTP/FTP/CUE/均衡器/淡入淡出/刮削/智能歌单/逐字歌词/指纹去重三层/DMR 记忆/FTP 退避/会话补全…）+ 播放故障三连修完（OOM/无声/卡顿，用户亲报 P0）。
- **停滞的**：用户每天看到的 UI 层——「四处 Comp 页待改造」原样挂了 9 批；灰显契约（写进 03-10 §9 B06/B09 与 PRD §4.4）**UI 层零落地**；`pixel_level_1to1=False` 从 11-16 挂到今天；九项视觉判读从未收口。

一句话：**后端冲到了 V0.3，前端体感停在 V0.1 半成品**。用户感知「越来越差」的来源见 §3~§6 逐条实锤。

**机制性根因（为什么必然长成这样）**：

1. **验收表没有 UI 质量判据**：PRD §10 十一项全是功能/性能判据；`pixel_level_1to1=False` 不构成任何红灯 → UI 项永不产生批次压力。
2. **无设备窗口时的偏科**：纯 JVM 功能项（指纹/智能歌单/退避算法）不依赖设备与视觉判断，天然适合夜间/无人值守批次；UI 改造需要真机判读闭环 → 被 pending-device 无限顺延。两股力量叠加 63 批，用户体感层一动不动。
3. **文档权威失真**：UI 现行规格（飞牛统一口径、导航模型、灰显契约）从未回写 PRD §7 / 03-10 §4/§5 正文——两者分别停在 2026-11-04 与 2026-11-06，靠 docs/12 批次叙事「续命」。「文档驱动开发」事实上退化为「批次日志驱动开发」，任何接手者（含 AI）从权威文档读到的都是错的。

## 8. 「体验越来越差」的体感归因（对用户感觉的正面回应）

1. **元数据降级直接可见**：冷扫优化（§61.203）让远程曲目大面积失去专辑/年份 → 首页/列表「未知」刷屏 + 副题空段——这是**最近才出现**的体验劣化，用户感知准确。
2. **界面反复改但从不收口**：底栏三 tab→四 tab、搜索钮加→删、底栏隐藏→恢复、播放页系统栏三轮调整——每批都「正确」，但从不经过一次**全页风格统一**的收口动作，视觉从未进入收敛轨道。
3. **不可用状态不可见**（§5 O1/O5）：断网/断源时点歌报错，用户把「列表看起来正常」感知为「App 越来越差」。
