## 2. 语义澄清（写清再实验，防误判）

### 2.1 START_STICKY 的官方语义边界

- 进程被杀后系统**择机**重建 Service（`onStartCommand(intent=null)`）——「择机」由
  系统调度决定，**无时限承诺**；MIUI 的电源管理会显著推迟/抑制后台重建。
- §61.32 前台 crash ~100ms 恢复走的是 **Activity 重建**（用户在前台看得到 UI），
  与 START_STICKY 无关；后台 206s 无重启 = MIUI 对后台进程拉活的限制，**不是
  START_STICKY 代码缺陷**。
- 因此「G09 crash 恢复」的代码层改进空间极小：Service 重建后的恢复链已存在
  （restore → prepare → PAUSED）；缺的是**进程重建本身**——这不在应用代码完全可控
  范围内（MIUI 权限域）。

### 2.2 onTaskRemoved 语义澄清（防错位施工）

`onTaskRemoved` 触发条件 = 用户从最近任务划掉应用（task 移除），**crash 不触发它**。
覆盖 onTaskRemoved 解决的是「用户划掉后服务是否继续」的产品口径问题，与 G09
（crash 恢复）**无关**。竞品口径待真机判读（划掉后音乐是否停）——如拍板做，应作为
独立小批，不并入 G09。

### 2.3 MIUI 自启动白名单（引导口径的唯一可行动点）

PRD §9 锁定**不申请** `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（且个人自用范围下
申请系统级豁免收益/风险比差）。MIUI 对「后台进程拉活」的主要放行开关 =
**设置 → 应用管理 → [应用] → 自启动**（per-app toggle，无需任何 API）。
应用侧能做的 = **检测 + 引导文案**（用户手动开启），这正是 §61.32 结论的正确延伸。

## 4. MIUI 自启动引导文案草案（V1 施工单）

- 行标题：`后台播放保活（MIUI）`
- 行副文案（检测到 MIUI 且自启动未开时）：
  > MIUI 会限制后台应用被系统重新拉起。若遇到播放页崩溃后音乐停止、需要手动重开
  > App，请开启「自启动」：设置 → 应用管理 → 云音乐 → 自启动。本应用不会申请
  > 电池优化豁免（PRD §9 口径），保活以您手动开启为准。
- 跳转动作：`Settings.ACTION_APPLICATION_DETAILS_SETTINGS`（包名 URI，无敏感权限）；
  非 MIUI 设备隐藏该行（`Build.MANUFACTURER` 判定，检测失败按非 MIUI 处理）。
