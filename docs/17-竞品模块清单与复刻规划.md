## 0. 结论先行

## 1. P0 不可变基线：核心播放逻辑复用竞品二进制

### 1.1 现状证据（已落地，不需重做）

| 项 | 证据 | 出处 |
|---|---|---|
| 竞品 native so 原样入库 | `engine-legacy/src/main/jniLibs/arm64-v8a/` **18 个 so**；APK 内实测 **20 个 so**（18 竞品 + AndroidX DataStore native 等） | `12 §32` / `12 §61.35` |
| 引擎指纹 | 1 个 `ENGINE-FINGERPRINT`，C6 全绿 | `12 §32` |
| 门面换绑 | `EngineAdapter : IMusicEngine` 落地并换绑 `EngineModule`，门面零改动 | `12 §36`（D-08） |
| JNI 真类 | 路线 A：84 个 JNI 真类 + 按需 slot（≤200），登记簿 51 行；舱内 54 Java + 2 Kotlin | `09 §2` / `12 §35` / `12 §36` |
| 真机出声 | Redmi K60 / Android 13 / arm64-v8a，引擎舱 A/B/C/D 全 PASS，**真机出声确认** | `12 §61` / `12 §61.32` |
| A3 验收 | G01~G07 PASS / G08 PASS（20 分钟口径，21 分 49 秒未被回收、异常 0）/ **G09 PARTIAL**（MIUI `fg service restriction` 抑制后台重启，非代码缺陷） | `12 §61.32` |
| 播放链入口 | `SourceConfig.cacheLocal=true` + `NMVirtualFileManager.SetConfig(cacheDir)` 进 normal mode，Memory Mode 的 FIFO 错位与 `OnWriteNetData Failed Not Support` 消失 | `12 §61` / `01 §6.1` 口径演进批注 |

**结论**：用户第 ① 条「核心播放逻辑直接复用竞品二进制」**已满足**，本轮把它升格为 **P0 冻结基线**：后续所有 UI / 交互 / 模块规划都不得触发引擎重写、不得换 `IMusicEngine` 门面、不得改 `EngineModule` 绑定。

### 1.2 必须如实标注的边界（不夸大）

- 现状是 **native so 二进制原样复用**；Java / JNI 层是按 `12 §10.2` 路线 A「**jadx 反编译重建 84 个 JNI 真类 + slot 空壳**」，不是把竞品 dex 二进制整包塞进 APK（`09 §2`：Java 层 jadx 反编译重建源码，不打包 dex 片段）。
- **用户 2026-11-09 13:01 已拍板确认**（`12 §61.44`）：「P0 现状是『native so 原样复用 + Java/JNI 层 jadx 重建源码 + slot』，**没问题**」→ 该边界**已获接受、不再是待拍板项**，本项目不追求整包 dex 二进制复用，`02 §0 A4` / `09 §2` 路线 A 定案保持不变。「连 Java 层也原样复用 dex」仅作为历史备选路线留档，不执行。
- P0 剩余断点（非本轮任务）：G09 保持 PARTIAL → 舱**不冻结**、`engine_compat_test` **不回填**、ABI 验收回填 + `§61.33` Manifest 生产形态施工单待 A3 全绿后推进；T-V 中需 USB / DMR 设备的项仍属硬阻塞。

### 8.1 为什么这是首要目标

用户第 ② 条把开发重心从「UI 1:1 复刻」转到「调通全格式播放内核」，§4 的 P2 因此**顺延、不是取消**。理由由实证给出，不是猜测：

- **native 能力远大于验证范围**：`libffmpeg.so`（6,658,592 字节）编入 **75 个 `ff_*_demuxer` / 100 个 `ff_*_decoder`**（69 个音频相关）+ 3 个专用解码库（`libnecmFlacDec.so` / `libnecmMP3Dec.so` / `libnecmAACDec.so`）。
- **A3 G01 真机只验证 4 种格式**：mp3 / flac / m4a(aac) / ogg(vorbis)，全部是 **URL 回环源的 12s 正弦音夹具**（`a3-phase-ab-evidence-2026-11-07.md §26`）；**LOCAL 源（SAF / MediaStore）全格式能力未验证**。
- **6 处格式白名单互不一致**：`ObjectType.AUDIO_EXT` 14 项 / `ScanRules.audioExt` 8 / `StrmPaths.defaultFilterTypes` 9 / `MimeHint.MAP` 9 音频 / `PlayerController.mimeHintOf` 6 类 / `DidlLiteBuilder.mimeOf` 6 类。扫描器与 strm 会直接过滤掉 `aiff, ape, dff, dsf, tak, wv`。
- **格式识别链有语义错配**：`EngineAdapter.kt:405-416` 把 `extension` 传进 `ResourceInfo`（so 的 JNI 字段表只从它读格式）；**LOCAL 源 `source.url == null` 时 fallback 到 `source.mimeHint`，而那是 `audio/mpeg` 这类 MIME 字符串、不是扩展名**，代码注释自述「待真机验证的假设，不是已证实的修复」。
- **两条取流路径只验了一条**：`createDataRequestHandler()` 仅 URL 源返回 `UrlDataRequest`（HTTP Range），LOCAL 源返回 `null` 由 native 直读 `localPath`。
- **已知掩盖**：m4a（`moov-at-end`）触发 `Start→push→onEnd→Read 0→重试` 死循环，当前用「成功 EOF 延迟 2s」掩盖（`UrlDataRequest.kt:80-86`），非根治。

### 8.2 「全格式」的客观定义

以 `libffmpeg.so` 实际编入的 `ff_*_demuxer` + `ff_*_decoder` 交集为候选集，逐格式在 **REMOTE（URL / 回环）与 LOCAL（SAF / MediaStore）双路径**下真机通过。判据沿用 G01：`Open codec for <codec>` → `Write start play` → 完整时长 → `ENDED` → 自动进曲，附加 seek / pause→play 位置连续 / 零崩溃。

**不得写成「已支持」**：仅 demuxer 字符串存在、仅 JVM 单测通过、仅 URL 夹具通过、仅静态白名单补齐、LOCAL 未测。

### 8.14 F4 native 分支语义的一手二进制复核（`12 §61.54`，2026-11-09 20:07）

> 设备仍离线 → 本批**纯离线 / 只读 / 零生产代码改动 / 零设备操作**。
> 报告 `analysis/l3-f4-disasm-verify-report.md`。

**动机**：§8.12 的 kind 槽假设当时只**引用** `docs/12 §59.2` 的文字记录。
本批直接反汇编 `libNMCommonCache.so` 并解析 `.rela.dyn` 的 GOT 重定位，
把该假设的 **native 侧前提**升级为 **so 字节级一手证据**。

**一手证据**（`OnNetSourceDataDone @ 0xbee8`, size 384；工具
`tools/l3_f4_disasm_verify.py`，capstone + pyelftools 本机既有、零新增依赖）：

```
0xbf08  cmp  w1, #2            ; 首参 w1 = kind
0xbf14  b.ne #0xbfa0           ; kind!=2 → 另一分支
0xbf5c  ldr  x9, [x9, #0xed0]  ; kind==2：GOT 0x4bed0
0xbf7c  bl   #0x16468          ; 投递队列（分支 1）
0xbfe4  ldr  x9, [x9, #0xee8]  ; 其余：GOT 0x4bee8
0xc004  bl   #0x16468          ; 投递同一队列（分支 2）
0xc034  blr  x8                ; 队列取出后虚调用执行 task
```

| GOT 槽 | `.rela.dyn` 符号（`GLOB_DAT`=1025, addend 0） | 地址 | 触发 |
|---|---|---|---|
| `0x4bed0` | `PreloadDoneTaskOnWriteThreadEv` | `0xb86c` | `kind == 2` |
| `0x4bee8` | `OnFlushNetDataEv` | `0xc068` | `kind != 2` |

两分支构造的任务对象结构完全一致，唯一差别是 GOT 槽取出的函数指针，
且都投递同一队列 —— 排除「只是不同日志/统计路径」的可能。
发布 so **已 strip 无 `.symtab`**（仅 256 个 `.dynsym`），首版脚本因此抛
`AttributeError`，本批修为 `.symtab or .dynsym` 兜底。

**结论分层**：**已证实**的是 §59.2 的分支语义（§8.12 假设的 native 前提）；
**仍待验证**的是「`UrlDataRequest.kt:96` 传 `requestId` → `id==2` 被误判为
kind → fMP4 REMOTE 提前 `PreloadDone` → 重发同区间 → 无 codec」这条**因果链**。
