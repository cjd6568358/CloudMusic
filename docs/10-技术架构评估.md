## 1. 总体评价

### 1.1 一句话结论

「数据源 ←`Link`→ 内核 ←`IMusicEngine`→ 输出」的三段解耦是本架构的承重结构，设计正确且各文档已对齐；**当前最大的不确定性不在文档而在实现**——jadx 反编译引擎舱 Java 层的实际闭包大小，是唯一可能推翻 A1（照搬竞品内核）决策的未知数，必须作为编码第一件事先行验证（§2 R1）。

### 1.2 评审确认的优点（保持，不动）

| # | 优点 | 评审意见 |
|---|---|---|

### 1.3 关键取舍评价

| 取舍 | 评审结论 |
|---|---|
| 单进程 vs 竞品「主 + `:play` + 5 MpService + AIDL」 | **正确**。竞品多进程主要为插件容器与在线业务隔离，本地播放器不需要。代价 = 引擎 native 崩溃即全进程死——原文声称可「进程内捕获后重启舱」属技术性错误，已修正为 sticky 重启 + Room 恢复（§2 R2）；`IMusicEngine` 门面保留未来拆 `:engine` 独立进程的选项 |

## 2. 风险与问题分级（P0 / P1 / P2）

### P0

**R1 · 引擎舱 Java 闭包未实测——编码第一件事（spike #0）**

- 现状：`05` 只完成了二进制侧（JNI 符号 / `DT_NEEDED`）；Java 侧闭包大小、`playerengine.*` Java SDK 的真实依赖均未测（`05 §7` 自认）。
- 证据（本轮 dex 字符串实测）：JNI 绑定横跨 **4 个包族**（`playerengine` 121 导出、`playlist.core` 31、`sdk.NMCommonCache` 58、`media` 2）；`classes14/18` 中 `PlaybackEngine` 语境与 `NMVirtualFileManager`、`BizMusicMeta`、`automix`、redux 风格混淆类（`Ljo0/c` 等）交织——**闭包大概率超出 `playerengine` 子树本身**。
- 处置（已写入 09 §5 编码顺序）：jadx 到手后先做 **1~2 天时间盒的闭包测量 spike**：反编译 → 列 `playerengine.*` 全部 import 闭包 → 产出裁剪清单。**判据建议**：闭包 ≤ ~150 个类且不拖入 redux / 在线业务 → 走 A1；明显超出 → 按 03-06 §2 用 dex 片段临时兜底并登记，兜底比例过高则启动 `:engine-opensource`（FFmpeg + Media3/ExoPlayer）评估。判据数值由用户在 spike 后拍板。
- 连带依赖 spike 结果的项：so 打包集（R3）、R8 keep 的 3 个「示意包名」校准、`PlaybackDataSource` 实际方法签名（03-06 §5 适配层当前是假设）。

**★ 实测补记（2026-11-05，见 `docs/11-spike0-Java闭包实测.md`）**：本机无 jadx，已用纯 Python 解析 20 个 dex 的类引用图完成等价实测（`tools/spike0_java_closure.py`）。从 4 个 JNI 包族 84 个类出发，**全量可达闭包 135,954 个类（占全 App 178,120 的 76.3%）**，业务耦合信号 16,091 个 → **原判据两项均不通过，A1「整舱照搬」不成立**；但入口面很窄（最小舱内 84 个类 + 一层边界 160 个，P3 复核纠偏见 `11 §9`），耦合是第 3 层起的间接传递。R8 keep 已校准为 12 个精确类 / 210 个 native 方法（与 `05` 的 212 个 so 侧导出高度吻合）。**引擎舱实现路线已于 2026-11-05 拍板为 A（薄门面 + 边界 slot，slot 后期按需实现），见 `11 §6` / `12 §10`；A 不推翻 `09 §2` 口径，故该口径保持不变**。

**R2 · native 崩溃恢复语义错误（本轮已修正）**

- 原文（02 §10 / 03-06 §12.6 / 07 §5 / 03-06 §9 状态机表）：「前台服务捕获 native 崩溃信号 → 重启舱 → 恢复队列」。
- 错误原因：单进程下引擎 so 的 SIGSEGV/SIGABRT 即**整个进程退出**；进程内 signal handler 捕获后继续运行属未定义行为，且与 `debuggerd`/tombstoned 冲突，不能作为架构承诺。竞品用独立 `:play` 进程正是为此。
- 修正（已改进 02 §10、03-06 §6.2 G09 / §9 / §12.6 / §13、07 §5）：`START_STICKY` → 系统重启服务 → `onCreate` 从 Room 队列游标恢复（保持 PAUSED）→ crash 标记文件判定「上次异常退出」→ UI 提示。Android 12+ 后台 FGS 重启限制的降级路径（先恢复数据、等用户交互再开播）已写入 03-06 §12.6。
- 诚实代价：单进程方案**明确放弃**了竞品的崩溃隔离（原文称之为「能力补齐」不成立）；G09 改为验证「重启后 ≤5s 回到可播放态」。

**R4 · 明文凭据 × Android 自动备份（建议直接采纳）**

- `AppSettings`（DataStore）明文存 WebDAV 账号密码（决策 ④，前提是「个人自用」）；但 Manifest 默认 `allowBackup=true` 会让系统把该文件**备份上云**（换机迁移 / 云备份），与「数据不出本机」的定位相悖。
- 处置：`android:allowBackup="false"` 已按建议值写进 03-11 §1.1 模板并注明理由；未来若要备份能力，改用 `dataExtractionRules` 排除 DataStore 文件。零成本。
- **★ 拍板结论（2026-11-05）**：**采纳**，作为 Manifest 基线，不再保留 `allowBackup=true` 的任何变体；C3 静态检查增加「合并后 Manifest 必须含 `allowBackup=false`」断言，防止 module Manifest 覆盖。

**R5 · strm / 播放列表双通道摄入歧义（已澄清，03-04 §5）**

- 原：03-04 §5 走查分类写「`.strm` → StrmDriver 解析」，而 03-03 的 StrmDriver 是**委托型挂载**（绑定自己的 Storage / `paths`）；两条摄入路径并存且未说明 Local 挂载里扫到的 `.strm` 归谁处理，存在同文件双重入库的歧义。
- 修正：任意 Storage 走查中的 `.strm` / `.m3u*` / `.pls` 由扫描器**直接调用 03-03 共享解析函数内联展开**（不实例化驱动）；StrmDriver / PlaylistDriver 挂载仅用于 `paths` 映射 / autoFlatten / 跨挂载虚拟目录场景；跨路径重复按 PRD §13 #14 允许共存、UI「合并重复项」折叠，V0.1 不做跨路径去重。

**R6 · `preferProxy` 能力位自相矛盾（已修正，03-01 §4 / 03-02 §1 / 03-08 §3）**

- 原：03-01 定义 `preferProxy`「WebDAV 默认 true、谁读 03-08」，但 03-08 决策表对 `PROXIED` 只看 `directUrl()`——二者对 WebDAV 默认场景给出**相反结论**（直链优先 vs 一律代理）。
- 修正：`preferProxy` = **驱动级投屏默认**（默认 false，与决策 3 直链优先一致）；投屏生效值 = 用户 `forceWebdavProxy` **或** 驱动 `preferProxy`；为 true 时跳过 `directUrl()` 探测直接代理。三处文档已对齐。
