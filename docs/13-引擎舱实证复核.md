# 13 · 引擎舱实证复核（spike #1）

**日期**：2026-11-05
**触发**：用户「继续」→ 按 `12 §7 #6` / `11 §7` / `10 §4 #5` 推进不依赖 jadx / Android SDK 的实证复核
**方法**：纯 Python 解析 20 个 dex 的 `code_item` 指令（`tools/spike1_engine_audit.py`，复用 spike #0 的 `DexFile`）+ baksmali 3.0.10 定向反汇编 + APK 内 ELF64 / `.rodata` 字符串直读
**结论**：**三项挂账全部落地，并发现 1 个 P0 级打包缺陷与 1 处契约级错误假设**：
1. Java 层几乎不直接调 `System.loadLibrary`，而是统一走混淆封装器 `zv.a.b(Context, libName, stack)`；复核后 **17 个打包集名单中的裸名全部有加载证据**，但发现被误列为「系统库」的 `libc++_shared.so` 实为 5 个入口/依赖库的 `DT_NEEDED` 直接依赖且必须随 APK 打包 → **打包集修正为 18 个 / 18.5 MiB**。
2. `PlaybackDataSource` **不是数据源接口**（是预加载 / 引擎缓存配置类），`03-06 §5` 的适配层假设错误；真正的音源接口是 `playerengine.DataProvider`。
3. `libnmplaylist.so` 自带完整 SQLite 队列持久化（5 张表 + `nativeInit(db_path)`），**不是只读镜像**，`03-06 §8` 双轨设计需补隔离约束。
4. **（2026-11-05 续，见 §7）** 复核 `03-06 §5` 其余映射行：竞品有 `AudioPlayerUnit` / `Playback` / `PlaybackEngine` **三层并行播放 API**，文档假设的 `create()` / `getPosition()` / `release()` 等公开方法**都不存在**（真正入口是 Kotlin `external` native 方法本身）；并精确解释 C1 的「JNI 导出 202 vs dex 210 差 8」——`Playback.nativeNotifyAudioEffectChanged` 1 个 + `PlaylistJniBridge` 7 个。
5. **（2026-11-05 续二，见 §8）** 校准照搬舱类名与 R8 keep：`03-07 §2.1` 的 `AudioFocusKeeper` / `AudioFocusHolderWrapper` **只是字符串常量、没有类定义**；落地 `engine-legacy/proguard-rules.pro`（12 个精确 JNI 类 + 4 个包族通配 + 媒体会话精确类），并让 C1 校验全部 202 个 `Java_*` 符号类的 keep 覆盖，长期 WARN 消除。

> 本报告不改动 R3「闭包打包」的决策口径，只修正闭包定义中的一处事实错误（`libc++_shared.so` 非系统库）。历史文档里出现的「17 个 / ~17.6 MB」均为修正前口径，**以本文 §2 与 `03-12 §4` 的 18 个为准**。

## 2. `System.loadLibrary` 全局复核 → 打包集 17 → 18（P0 修正）

### 2.1 实测数据

| 项 | 结果 |
|---|---|
| `System.loadLibrary` 直接调用 | **3 处**（去重后），全部在 `classes.dex` 的加固壳 `com/netease/nis/wrapper/`；参数是加密串（如 `IAAHAAI=`），2 处运行时拼接未解析 |
| 统一封装器 `Lzv/a;->b(Landroid/content/Context;Ljava/lang/String;Ljava/lang/String;)V` | **36 处 / 20 个可解析裸库名**，另有 2 处动态拼接未解析（`Lwg/d;.h`、`ReLinker.loadLibrary`） |
| 17 个打包集裸名 | **全部在 dex 的 `const-string` 中出现**，且多数就在 JNI 类的 `<clinit>` 里（如 `AudioPlayerUnit.<clinit>` 同时引用 `ncmplayerengine` / `ncmaudioplayer` / `NMCommonCache` / `neaudioeffects`） |
| 4 个软解器 | 由推测升级为实证：`necmMP3Dec` 5 处 / `necmAACDec` 7 处（classes15 `MediaGiftClient.<clinit>` 等）、`necmFlacDec` / `necmMediaCodecJDec` 在 classes16 `necmMediaPlayer.<clinit>` |
| 封装器加载但**不在原 17 个打包集**的 11 个 | `AeTimeline`、`Core_MNN_JNI`、`NeAREngine`、`NeAVEditorTimeline`、`NeFace`、`NeImageCrop`、`YUV`、`c++_shared`、`fpGenerate`、`neaveditorutility`、`pcmextract`（其中 `c++_shared` 经 §2.2 补入；**其余 10 个不追加**） |

典型加载点（baksmali 实证，`classes5.dex`）：

```smali
# NMVirtualFileManager.loadNative(Context)
const-string v0, "NMCommonCache"
const-string v1, "com/netease/.../NMVirtualFileManager.class:loadNative:... line-25"
invoke-static {p0, v0, v1}, Lzv/a;->b(Landroid/content/Context;Ljava/lang/String;Ljava/lang/String;)V
```

即：**库名以裸名字符串传给封装器，封装器内部再决定 `System.loadLibrary` / ReLinker / SoLoader**。这解释了为什么按 `System.loadLibrary` 直接调用点统计会得到「只有 3 处」的表象。除 `c++_shared` 外，其余 10 个打包集外的库全部属于视频编辑 / AR / 人脸 / 音频指纹 / PCM 提取 / 在线 AI 推理（`Core_MNN_JNI`），与 V0.1 播放无关，`PRD §3 / §6.4` 明确不做，不追加。

### 2.2 P0 缺陷：`libc++_shared.so` 被误列入系统库白名单

`tools/elf_probe.py` 原把 `libc++_shared.so` 放在 `SYSTEM_LIBS`（不打包），但实测：

| 证据 | 值 |
|---|---|
| 入口 / 依赖库的 `DT_NEEDED` | `libncmplayerengine.so`、`libncmaudioplayer.so`、`libaudioplayer.so`、`libNMCommonCache.so` 等 **5 个库直接依赖** `libc++_shared.so` |
| 竞品 APK | 自带 `lib/arm64-v8a/libc++_shared.so`，**968.7 KB**，ELF64 / EM_AARCH64(183)，`DT_NEEDED = [libc.so, libdl.so]` |
| Java 侧 | `zv.a.b(..., "c++_shared", ...)` 在 `AVEditorNativeMethod` 等 4 处显式加载 |
| NDK 口径 | `libc++ is not a system library. If you use libc++_shared.so, it must be included in your APK`（Stack Overflow / NDK 文档；缺失时 `UnsatisfiedLinkError: dlopen failed`） |

**影响**：若按原 17 个清单提取，运行时加载任何一个入口库都会因找不到 C++ 共享运行时直接失败 → G01 播放用例无法通过，属发布阻断。原 C1「递归闭包无越界」之所以没报，是因为白名单把它提前跳过了。

**处置**（已落地并验证）：
- `tools/elf_probe.py`：`libc++_shared.so` 从 `SYSTEM_LIBS` 移入 `PACKED_LIBS`（**18 个**），注释写明依据；
- `tools/check-engine-abi.py`：`EXPECTED_KB` 补 `968.7` KB，C1 文案 17→18；
- `tools/extract-engine-libs.py` / `check-fingerprint.py`：文案与指纹头同步 18；
- 打包集总量 **18 个 / 18.5 MiB**（dry-run 实测），`DT_NEEDED` 递归闭包 **14 个**打包集内 so、无越界。

**验证**：`pre_release_check.py --mode dev` C1~C6 **6/6 PASS**（18 个齐全 / 架构 / 大小 / 闭包全通过）、`--mode release` 仍正确阻断（C1/C3/C6 FAIL）、`extract-engine-libs.py` dry-run 18 个 / 18.5 MiB、`check-fingerprint.py --emit` 18 行、`py_compile` OK。

> **2026-11-05 第十批后续**：`:app` Manifest 落地后 **C3 转为实测 PASS**（11 项权限 / 白名单 / `allowBackup=false`），release 阻断项相应变为 **C1 / C6**，见 `12 §19`。上式为本轮历史实测记录。

> 历史数据仍成立：`167 个 / 125.6 MiB` 是提取侧上限，闭包外冗余仍约 `107.5 MiB`。R3 决策「只打闭包、不进 167 全集」不变，只是闭包里多了一个必须随包的 C++ 运行时。

## 3. `PlaybackDataSource` 方法签名 → `03-06 §5` 契约级修正

baksmali 定向反汇编 `classes14.dex`（权威）＋ dex 指令解析（交叉验证）结果一致：

```smali
.class public final Lcom/netease/cloudmusic/android/sdk/playerengine/PlaybackDataSource;
.field private volatile nativeHandle:J
.field private final musicInfo:Lcom/netease/cloudmusic/android/sdk/playerengine/MusicInfo;
.field private volatile preloadCallback:Lcom/netease/cloudmusic/android/sdk/playerengine/PreloadCallback;
.field private volatile engineCacheLoadConfigHandle:J
```

| 类别 | 方法 |
|---|---|
| 7 个 native（与 `11 §3.2` 的计数**完全吻合**） | `nativePreload(JJ)Z`、`nativeCancelPreload(J)Z`、`nativeRelease(J)V`、`nativeRetainEngineCacheLoadConfigHandle(J)J`、`nativeReleaseEngineCacheLoadConfigHandle(J)V`、`nativeSetEngineCacheLoadConfig(JJJJJJ)Z`、`nativeSetPreloadCallback(JZ)Z` |
| 公开 API | `preload(J)Z`、`cancelPreload()Z`、`close()V`、`setEngineCacheLoadConfig(EngineCacheLoadConfig)Z`、`setPreloadCallback(PreloadCallback)Z`、`getMusicInfo(): MusicInfo`、`takeNativeHandle$playerengine_release()J`、`onNativePreloadResult(IJJI)V` |

**它是「预加载 + 引擎缓存配置」的 JNI 桥，没有任何 `open/read/readAt/getMimeType` 字节流方法**；唯一的 `close()` 是释放 native handle。`03-06 §5` 的 `LegacyDataSourceBridge : PlaybackDataSource` 假设**不成立**。

真正的音源交付接口是 **`com.netease.cloudmusic.android.sdk.playerengine.DataProvider`**（`classes14.dex`，`public interface abstract`）：

| 方法 | 语义（对本项目 `Link` 三态的映射） |
|---|---|
| `getUrl(): UrlResult` | `Link.Kind.URL` / `PROXIED` 的直链或本地代理 URL；`UrlResult` 是 Kotlin data class（`url, fileSize, format, expiresAt, realBitrate, md5`） |
| `getLocalPath(): String` | `Link.Kind.LOCAL` 的本地路径 |
| `openLocalFd(String): Int` / `closeLocalFd(Int)` | 本地文件描述符交付（竞品 native 自己读，Java 层不喂字节流） |
| `onExpire(String): UrlResult` | 直链 403 / 签名过期时重签，对应 `07 §8` 与 `03-08` 回落代理 |
| `setDataRequestErrorCallback(DataRequestErrorCallback, Z)` | 上游错误透传 |
| `createDataRequestHandler(): Object`、`cancelRequest()`、`close()` | 请求生命周期 |

**修正口径**：`LegacyDataSourceBridge` 应实现 `DataProvider`，把 `IDataSource` / `Link` 三态映射为上表；`:core-model` 的 `IDataSource.open(offset)/readAt()/mimeHint()` 是**自研契约，保持不变**（03-08 本地 HTTP 代理仍直接消费它）。`PlaybackDataSource` 归入预加载/缓存配置，与数据源适配解耦。这正是 `03-06 §5` 原注「以实际 dex 为准改适配层，不改 `IDataSource`」所授权的动作。

> **★ 传导结论（2026-11-06 补，`16 §3`）**：本节实证同时意味着 **`proxy` 态（WebDAV 鉴权流等无直链形态音源）的本机播放必须经本地代理转 URL**——引擎舱没有 Java 字节流入口，`IDataSource` 只能经代理回源被消费。原「本机播放完全不经代理」口径（架构 §5 / §7.4、03-01 §5、03-06 §7 / §16 #6、03-08 §1 / §8.4 / §14 #1）已在同日全部修正；**C-05 / C-06 已由第十二批落地**（`12 §21`）：`EngineSource` 补 `url` / `localPath` 可选字段，`ProxyStartPolicy` 补 `localPlaybackKind`（④）。

> 顺带确认：`NMCommonCache.SourceDataRequest` / `NMBufferSource` / `NMVirtualFile` 都是 `InitPtr/DeletePtr` 型句柄包装，不是字节流接口；`module.player.datasource.IDataSource` 是业务层元信息接口（`getBizMusicMeta()` / `supportCacheFile()` 等），也不要误当适配目标。

## 4. `libnmplaylist` 的 native 持久化路径 → 双写风险证实

`10 §4 #5` 要求确认「native 侧不与 Room 抢状态」。ELF `.rodata` 直读结果：**风险属实**。

| 证据 | 实测 |
|---|---|
| 自建表 | `playlist_current_pointer`、`playlist_music_item`、`playlist_snapshot`、`playlist_snapshot_gc_queue`、`playlist_store_meta` 五张 `CREATE TABLE IF NOT EXISTS` |
| SQL 能力 | `INSERT` / `SELECT`（含 `ROW_NUMBER() OVER` 窗口函数）/ `UPDATE` / GC 队列清理 / `playlist_store_meta` schema 版本 |
| 状态字段 | `current_snapshot_id`、`origin_snapshot_id`、`current_index`、`seek_position`、`played_time`、`play_mode`、`mode_state_json`、`music_raw_data` |
| JNI 导出 | `nativeInit`、`nativeSetDbAdapter`、`nativeRestoreFromDb`、`nativePersistList`、`nativeUpdatePlaybackPosition`、`nativeGetPlaybackPosition`、`nativeListRecentPlaylists`、`nativeReadSnapshotRawRange` 等 25 个 `PlaylistJniBridge` 方法 |
| 路径来源 | `playlist_core_init: db_path=%s, codec_type=%d, version=%s`、`Invalid db_path`、`sqlite3_open` → **db_path 由 Java 层经 `nativeInit` 传入**，native 自己开库写表 |
| 依赖 | `libsqlite3x.so` 是 requery SQLite 独立打包版（`io/requery/android/database/sqlite/*`），不是系统 SQLite |

即：native 侧**不是 `03-06 §8` 写的「只读镜像」**，它有自己的队列 / 快照 / 播放位置持久化，且自带恢复入口 `nativeRestoreFromDb`。若舱内初始化时给了真实业务目录，冷启动就可能出现「Room 与 native 两份队列状态」的双写分叉。

**处置（写入 `03-06 §8`）**：
1. 舱内 `nativeInit` 只传**隔离沙箱路径**（`noBackupFilesDir/native_playlist/` 或 `cacheDir`），明确标记为执行镜像缓存，不参与业务恢复；
2. **禁止**把 `nativeRestoreFromDb()` / `nativeListRecentPlaylists()` 的结果回写业务态；冷启动恢复唯一入口仍是 `Room.restore()` → `QueueSync.push()`（`03-06 §8.2` 单向全量下发不变）；
3. 各实例初始化时先全量 `push` 覆盖 native 侧残留，避免上次会话的快照被当成当前队列；
4. `03-05` 的 Room 9 张物理表（2026-11-06 口径修正，`16 §6`）与这 5 张 native 表**物理隔离、无跨库外键**，合规上也不触碰明文凭据。

### 7.3 `PlayerDataSource`：`DataProvider` 的真正接入点

`PlayerDataSource` 是**非 native 的 Kotlin 数据类**（5 个 getter，无 JNI）：`getDataProvider(): DataProvider`、`getResourceInfo(): ResourceInfo`、`getConfig(): SourceConfig`、`getSongId(): String`、`getSourceCallback(): SourceCallback`。

所以 §3 的 `LegacyDataSourceBridge : DataProvider` 结论成立，但**接入链要补一层**：

```
Link 三态 → LegacyDataSourceBridge(DataProvider) → PlayerDataSource
          → nativeEngineSetDataSource(handle, playerDataSource)
          → AudioPlayerUnit.nativeSetDataSource(handle, playerDataSource)
```

`DataProvider` 面向缓存 / 网络层（URL / fd / 重签），`PlayerDataSource` 才是直接喂播放器的封装，两者不是二选一。已回写 `03-06 §5` 代码块。

| 来源 | dex native | so 导出 | 差 | 具体方法 |
