## 1. 背景与目标

用户已有一批音乐资产分散在**手机本地**、**自建 NAS / 网盘（WebDAV 等）**和 **strm 直链文件**里，市面现有安卓播放器无法把它们当成同一个曲库来管理和播放（详见前期调研：安卓端只有 Kodi 能同时处理 strm 与本地音乐，但 UI 是电视盒子风格、体验差）。

因此自研一款**安卓原生、离线优先、以「统一虚拟曲库」为核心**的音乐播放器：

1. **一个曲库**：本地文件、网络挂载目录、strm 条目在 UI 里地位完全平等，可混合进同一个歌单、同一个播放队列。
2. **一套播放体验**：无论音源在哪，播放控制、通知栏、锁屏、蓝牙、DLNA 的行为一致。
3. **一份视觉参考**：交互与视觉风格参考 `NeteaseCloudMusic.apk`，开发期素材取自该 APK，后续替换为自有素材。
4. **可持续演进的数据源架构**：本期只做 WebDAV，但架构必须预留 SFTP / NFS / FTP，新增协议不改动播放层与 UI 层。

**成功标准（一句话）**：用户把手机文件夹、一个 WebDAV 地址、一个装满 strm 的目录加进来之后，再也不需要关心某首歌来自哪里。

## 4. 关键产品原则（后续架构不得违背）

1. **数据源无关性**：UI 与播放层只认识统一的 `Track` 模型，不认识「这个文件是本地的还是 WebDAV 的」。
2. **插件化数据源**：新增一种挂载协议 = 新增一个数据源实现，不改曲库、播放器、UI 一行代码。
3. **单一播放内核**：只有一个播放实例，所有音源走同一条播放链路，DLNA 投屏是该链路的一种「输出设备切换」。
4. **离线优先**：曲库元数据本地持久化；网络不可用时不崩溃、不丢列表，只把不可达条目标记为「暂不可用」。
5. **最小权限**：只申请功能必需的权限，不照抄参考 APK 的 84 项。
6. **读优先**：V0.1 对音源**只读**，不提供上传、删除、重命名等写操作（避免误删 NAS 数据）。
7. **竞品优先复制**：播放内核、UI 交互、外设能力（DLNA/蓝牙/格式解析）**全面照搬竞品**（NeteaseCloudMusic 9.6.20），匹配场景**像素级复制代码和 so**，避免 bug；竞品 native so 与 Java SDK 层**一次性反编译重建搬迁**（升级可能性不大，不做升级工具链），**优先复制使用而不是重写**。
8. **技术栈升级**：竞品技术栈如果存在可升级到最新稳定版的，建议升级；老旧历史兼容代码不移植。**但当「照搬竞品」与「升级」冲突时，照搬优先**（播放页唱片动画、音频焦点层已确认照搬，见 §13 #25/#26）。
9. **开源**：项目以 AGPL-3.0 开源，仓库公开；依赖选型需注意许可证兼容性。
10. **投屏直链优先**：DLNA 投屏时，除本地音乐必须经本地 HTTP 代理（nanohttpd）外，其余音源（strm 直链、WebDAV 可直连 URL、播放列表 URL 条目）一律把原始 URL 直推 DMR，不经手机中转；直连失败自动回落代理。

## 5. 功能边界 · 数据源与曲库

### 5.1 支持的数据源类型

| 类型 | V0.1 | 说明 |
|---|---|---|
| 本地目录 | ✅ | 通过 SAF / `READ_MEDIA_AUDIO` + MediaStore 双通道；可添加多个根目录；支持子目录递归 |
| WebDAV | ✅ | 服务器地址 + 端口 + 路径 + 账号密码；支持 HTTP/HTTPS、自签证书开关、Basic/Digest 认证；驱动实现参考 `OpenList-zig/drivers/webdav`（gowebdav 客户端） |
| `.strm` 目录 | ✅ | 见 §5.2；可位于本地目录、也可位于已挂载的 WebDAV 目录内 |
| SFTP / FTP / NFS | 仅架构预留 | 接口设计参考 `OpenList-zig/drivers/{sftp,ftp}` 驱动实现 |
| .m3u/.m3u8/.pls 播放列表 | ✅ | 解析播放列表文件，展开为曲目条目 |
| SMB / 对象存储 / 各家网盘私有 API | ❌ | 不做；需要时通过 strm 直链间接支持 |

### 5.2 `.strm` 规范（V0.1 支持范围）

- 文件为 **UTF-8 纯文本**，取**第一行非空、非 `#` 注释**的内容，trim 后作为音源 URL。
- **仅接受 `http://` / `https://`**；其他 scheme（`file://`、`ftp://`、`smb://`、`webdav://` …）不执行，统一标记为「不支持的 strm」并在 UI 里可筛选查看。
- 允许带 query / 签名参数（网盘直链常见）；**不解析** URL 内容、不做任何脚本/指令执行。
- 文件名（去扩展名）作为默认标题，形如 `周杰伦 - 晴天.strm` 时按 `艺人 - 标题` 兜底解析。
- 目录递归扫描；同一 URL 去重；不因一次播放失败删除曲目，只标记「链接失效」并保留记录。
- 直链过期/网盘风控属于外部问题，产品只负责**明确报错 + 一键重新扫描 + 批量重试**，不承诺自动续期。
- **`.m3u/.m3u8/.pls` 播放列表**：V0.1 支持。解析播放列表文件中的条目，展开为曲目加入曲库；条目可以是相对路径（相对于播放列表文件所在目录）、绝对路径或 URL。
- 播放列表解析逻辑参考 `OpenList-zig` 的 strm 驱动与文件系统驱动设计。

### 5.3 统一曲库模型（业务口径）

所有来源的条目收敛为同一个 `Track`，至少包含：
`ID(来源+路径/URL 的稳定哈希)`、`标题`、`艺人`、`专辑`、`时长`、`音源引用`、`来源类型`、`封面引用`、`标签完整度`、`可用状态`。

- **ID 稳定性**：同一文件重复扫描、挂载地址变更后应尽量保持 ID 稳定，避免收藏/播放记录丢失。
- **混合能力**：歌单、播放队列、搜索结果、排序、收藏均可跨来源混合。
- **去重口径**：允许同曲不同来源共存（已确认），UI 提供「合并重复项」开关。
- **不可用状态**：本地文件被删、WebDAV 失联、strm 直链失效 → 标记为「暂不可用」，灰显但**不自动移除**，恢复后自动可用。

### 5.4 扫描与元数据

- 触发：首次添加目录、手动「重新扫描」、App 启动时的轻量增量检查、前台下拉刷新。
- 能力：递归列目录、按扩展名白名单过滤、进度与可取消、增量（只处理新增/变更）、失败项汇总。
- 元数据：标题/艺人/专辑/曲目号/年份/流派/时长/采样率/位深/封面；**标签缺失时兜底用文件名与目录名解析**。
- 封面：内嵌标签优先 → 同目录 `cover.jpg/folder.jpg` → 占位图；不联网刮削（V0.1）。
- 格式白名单（V0.1）：`mp3 / flac / wav / m4a / aac / ogg / opus / wma` + `.strm`。
  `ape / dsf / dff / aiff / wv / tak / cue` 归 V0.2~V1.0，**格式探测以文件内容为准，扩展名只作初筛**。
- 排除规则：可配置忽略目录（如 `Android/`、`.nomedia`）、最短时长阈值（默认过滤 <10s 的碎片）。

## 6. 功能边界 · 播放与输出

### 6.1 播放内核（V0.1）

- 单一前台服务 + 单一播放实例；后台播放、锁屏控制、通知栏媒体卡片、耳机线控/媒体按键全部由**照搬竞品的媒体会话 / 音频焦点层**提供（见架构文档 §6.2）。
- 队列：顺序 / 单曲循环 / 列表循环 / 随机；支持手动排序、插播、移除、清空。
- 进度：记忆播放位置；切换音源后恢复队列；App 冷启动恢复上次队列。
- 错误处理：音源不可达、超时、解码失败 → 明确原因提示 + 自动跳下一首（可关） + 失败记录入口。
- 网络音源：支持 HTTP Range / 断点续读、缓冲策略；默认仅 WiFi 播放，移动网络开关可在设置中开启（口径演进 2026-11-08：**播放缓存改为写入 App 内部缓存目录** —— 用户拍板批准「路线 2」，见 `12 §61`；仅限 `context.cacheDir` 子目录、512MiB 上限、卸载即清、不外置存储不上传，替代原「缓存不落盘」口径）。**实现状态 2026-11-08**：`12 §61.28` 已落地播放前闸门（03-02 §344「由 03-06 检查」）与设置页「允许移动数据播放」开关；`03-11 §6 B05` 本地音源 / 飞行模式豁免不变。
- **不在 V0.1**：均衡器、音效、淡入淡出、变速、频谱、USB 独占、Hi-Res 认证、无缝衔接（gapless，放 V0.2）。

### 6.2 DLNA（V0.1 = DMC 投屏控制点）

- 同一局域网内通过 SSDP 发现 **DMR（媒体渲染器）**，列出设备供选择。
- **额外支持：主动指定目标 DMR**——不仅依赖广播发现，用户可手动输入 DMR 的 IP:Port 或 URL 直接连接（适配不支持 SSDP 广播的网络环境、跨网段场景、已知设备快速连接）。
- 支持：`SetAVTransportURI` 推送 → 播放 / 暂停 / 停止 / 跳转 / 查询进度 / 音量。
- 推送前把当前音源转换为 DMR 可访问的 URL，**直链优先**：strm / WebDAV 可直连 URL / 播放列表 URL 条目直接把原始 URL 推给 DMR；**仅本地文件**需手机端内置本地 HTTP 流代理（成熟库 nanohttpd）转发（参考 APK 亦为自写 SSDP/SOAP，见分析报告 §3.2）。直连失败（401/403/超时/直链过期）自动为该曲目回落代理。SFTP/FTP/NFS 无 HTTP 直链形态，届时仍走代理。
- 投屏期间：手机端作为遥控器，UI 显示设备名与播放状态；断连后回落到本机播放并提示。
- 多播/组播需持有 `MulticastLock`；退出投屏释放。
- **不做**：DMS（把手机曲库共享出去）、手机作为 DMR 被投。

### 6.3 蓝牙（V0.1）

- 依赖系统 A2DP 自动路由，App 侧不做音频通道切换。
- 通过**照搬竞品的媒体会话层**推送**标题/艺人/专辑/封面/时长/进度**给耳机与车机（AVRCP）。
- 监听蓝牙 A2DP 连接/断开：**断开时自动暂停**（可关）；连接时可提示「已连接 XX 设备」。
- 显示当前输出设备与编码格式（LDAC / aptX / AAC / SBC）为 V0.2 增强。
- **不做**：私有 BLE 协议、特定耳机 SDK、HiCar / Android Auto 深度适配、蓝牙设备配对管理。

### 6.4 音乐格式解析（V0.1）

- 覆盖 §5.4 白名单内的**容器识别 + 标签解析 + 内嵌封面提取 + 时长/音频参数读取**。
- 标签类型：ID3v1/v2、Vorbis Comment、MP4 atoms、APE tag、FLAC/WAV 元数据。
- 统一输出为 `Track`，解析失败不阻塞入库（降级为文件名信息）。
- **播放内核一次性搬迁**：从竞品提取的 native 解码库（`libncmplayerengine.so` 等）与 Java SDK 层（jadx 反编译重建源码）放入独立隔离舱，做一次性 ABI 验收后冻结；后续解包升级可能性不大，不投入自动升级工具链，**优先复制使用竞品 so 而非从头重写解码器**。
- **不做**：转码、格式转换、标签写回、音频指纹、云端曲目识别。

## 8. 明确的非目标（Non-Goals）

V0.1 及后续版本均**不**包含：

1. 任何在线音乐内容、搜索在线曲库、账号体系、登录注册、云同步。
2. 社交、评论、分享、动态、私信、关注、K 歌、直播、播客、视频、MV。
3. 会员、支付、广告、统计上报、推送（含各厂商推送 SDK）。
4. 参考 APK 的 React Native / WebView / 多进程插件容器 / AIDL 跨进程播放架构。
5. 桌面端、iOS、Web、车机原生适配、Android TV。
6. 非 arm64 架构（armeabi-v7a / x86 / x86_64）。
7. 竞品中的老旧历史兼容代码不移植（仅取最新有效实现）。

## 9. 权限边界（最小化）

## 11. 合规与「照搬实现细节」的落地口径

**用户已确认的口径（2026-11-04）**：

- **全面照搬竞品**：主题/播放内核 + 曲库 + 播放 UI + 外设能力（DLNA/蓝牙/格式解析）全面照搬 NeteaseCloudMusic 9.6.20，匹配场景**像素级复制代码和 so**，避免 bug。
- **优先复制而非重写**：竞品的 native so（`libncmplayerengine.so` 等 167 个库）和播放引擎 SDK **直接提取使用**，不从头重写。
- **so 一次性搬迁**（用户后续确认：升级可能性不大，按一次性开销算）：native 库存放在独立目录（如 `app/src/main/jniLibs/arm64-v8a/`），Java SDK 层用 jadx 反编译重建源码，整体封装为隔离舱并通过一次性 ABI 验收；仍保留 `IMusicEngine` 门面作为解耦边界与未来换开源引擎的逃生舱，但**不做自动解包升级工具链**。
- **技术栈升级**：竞品技术栈可升级到最新稳定版的，建议升级；老旧历史兼容代码不移植。**照搬优先于升级**：播放页唱片动画与音频焦点 / 媒体会话层按用户决策直接照搬竞品（§13 #25/#26），仅在照搬范围之外升级。
- **仅 arm64**：只保留 `arm64-v8a` 架构的 native 库，其他架构不提取。
- **品牌素材**：开发期素材取自竞品 APK（占位），**发布前全量替换**为硬性门槛（已在 §10 验收 #11）。
- **开源协议**：项目以 AGPL-3.0 开源；竞品 so 的使用需在 LICENSE / NOTICE 中声明来源与权利状况。

> **2026-11-05 架构决议补注（R3）**：上条「167 个库直接提取使用」指**提取侧全集**；`10 §2 R3` 拍板闭包打包后，实际随 APK 打包的只有 `DT_NEEDED` 闭包 ∪ 按名加载清单的 **18 个 / 18.5 MiB**（2026-11-05 spike #1 实证补入 `libc++_shared.so` 后由 17 个修正，清单见 `03-12 §4` / `13 §2`），其余留在 `analysis/` 备查。此决议不改变「优先复制而非重写」「一次性搬迁」口径，也不改变下方风险提示。

> ⚠️ **风险提示**：直接使用竞品 native so 存在著作权与 EULA 风险。作为个人自用项目，风险可控；若后续公开发布，需法务评估或替换为自有/开源解码方案（如 FFmpeg + ExoPlayer）。架构设计时将 so 访问层抽象为接口，保留未来替换可能。
