## 3. P0 修正：本机取流链路（spike #1 实证传导不彻底）

### 3.1 事实链

1. **spike #1 实证**（`13 §3` / `13 §7`）：竞品播放内核经 `DataProvider` 接收**音源定位符**（`getUrl()` / `getLocalPath()` / `openLocalFd()`），native 自行拉流；**Java 层不喂字节流**；`PlaybackDataSource` 是预加载/缓存配置类、不是数据源接口。`03-06 §5` 的桥接代码已按此重写：`PROXIED → UrlResult(url = proxy.resolve(link))`。
2. **未传导的旧口径**：`02 §0`（「内核接收字节流」）、`02 §1`（L2.5 描述）、`02 §5`（「本机播放不经过本地 HTTP 代理」）、`02 §7.2/§7.4`、`03-01 §5`（「本机播放不经 nanohttpd」）、`03-06 §7`（同句，**与自身 §5 直接矛盾**）、`03-06 §16 #6`（「禁止为本机播放启动 nanohttpd」）、`03-08 §1/§8/§8.4/§14 #1`（启动条件三个触发器全为投屏场景）。
3. **代码侧佐证**：`:output-localproxy/ProxyStartPolicy` 的输入是 `queueKinds / anyViaProxy / fallbackNeeded / settings`——**纯投屏语义，无「本机播放」维度**；按现语义播放 WebDAV 鉴权曲目时代理不会启动。
4. **影响定级**：PRD §10 #4 把「Basic 认证 WebDAV 播放」列为主线验收场景。引擎舱没有 Java 字节流入口，`proxy` 态曲目本机播放**只能**经本地代理回环取流；按旧口径实现将直接导致该场景不可用，故定 **P0**。

### 3.2 修正后的本机取流决策表（权威口径）

| `Link.kind` | 本机播放取流路径 | 本地代理 | `IDataSource` 的角色 |
|---|---|---|---|
| `URL` | 引擎经 `DataProvider.getUrl()` **自取**（native HTTP） | ❌ 不启动 | 不参与主链路（仅投屏回落与扫描 Range 读使用） |
| `LOCAL` | 引擎经 `getLocalPath()` / `openLocalFd()` 直读 | ❌ 不启动 | 不参与主链路 |
| `PROXIED` | 组合层 `proxy.publish(trackId, link)` → 引擎**回环自取代理 URL** | ✅ **启动（触发器 ④）** | 代理每请求经 `DataSourceAdapter.from(link)` 新建、按偏移回源 |
| `TEXT` | 扫描期已展开为 URL 条目；若直接播放按 `PROXIED` 处理 | ✅ 同上 | 同上 |

**不变的决策**：A9 投屏直链优先（`03-08 §3.1` 决策表原样保留）；省电目标（纯 `url` 态的本机播放与投屏**仍不启动代理**）；`IDataSource` 契约（03-01 §3）与 `IMusicEngine` 14 方法签名不动；本机播放与投屏**共用同一套回源原语**（03-08 §8.3 原则保留并强化）。
