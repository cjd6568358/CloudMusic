## 4. 本轮实证发现（重要，均不改变既有架构结论）

### D-01 · `analysis/decoded/lib/arm64-v8a/` 不完整

| 实测 | 值 |
|---|---|
| `analysis/decoded/lib/armeabi-v7a/` | 169 个 / 89.4 MiB，**全部 ELF32 / EM_ARM(40)** |
| `analysis/decoded/lib/arm64-v8a/` | **仅 1 个**：`libnesec-x86.so`，ELF64 / EM_X86_64(62) |
| APK 包内 `lib/arm64-v8a/` | **167 个 / 125.6 MiB，ELF64 / EM_AARCH64(183)** ✅ 与 `05` / `10 §2 R3` / `03-12 §4` 完全一致 |
| 抽样复核 | `libncmplayerengine.so` 814 KB / 13 项 `DT_NEEDED`（6 私有库 + libffmpeg），与 `05 §2` 一致 |

**判读**：`05` / `10` 的 ELF64 实测数据来自 **APK 本体**，结论正确；只是 apktool 解包产物未完整保留 arm64 库。`09 §3.1` 中「`analysis/decoded/` 为 05/06 实测依据」的措辞应按「APK 本体为 arm64 so 唯一完整来源」理解；`09 §3.1` 关于「`analysis/apk/` 可安全清理」的结论不受影响。

**处置**：C1 / C6 / `extract-engine-libs.py` 一律直接读 APK 条目，不依赖解包完整性；C1 在 decoded 目录不足 167 个时给出 WARN 提示。

### D-02 · 参考 APK 在 `arm64-v8a/` 目录内混放 x86_64 库

`libnesec-x86.so`（machine=62）位于 APK 的 `lib/arm64-v8a/` 下。它**不在 18 个打包集内、不会进本项目 APK**。C1 因此把「架构必须为 AARCH64」的强校验收窄到 18 个打包集，对提取侧全集的异常只记 WARN —— 否则一个与本项目无关的第三方库会误阻断构建。

### D-03 · JNI 导出 202 vs dex 侧 210（**2026-11-05 已逐方法定位**，WARN 保留但不阻断）

从 4 个入口 so 的 `.dynstr` 统计 `Java_*` 符号：118 + 2 + 24 + 58 = **202**；`11 §3.2` 的 dex 侧 native 方法为 **210**（`05` 的 so 侧记录为 212）。原推测为 `RegisterNatives` 动态注册或符号表口径差异，C1 记 WARN 并挂账到 `11 §7 #2`。
**spike #1 续轮（`13 §7.4`）已精确解释差额 8**：`playerengine` 差 1（`Playback.nativeNotifyAudioEffectChanged` 仅 dex 声明）+ `nmplaylist` 差 7（`PlaylistJniBridge` 的 7 组 `*Raw` 重载与 7 个日志 / 更新类方法，净差 7）；`NMCommonCache` 58/58 与 `NEAudioDevice` 2/2 完全一致。不是 R8 keep 漏类，**不影响 12 个精确类校准结论**。C1 的 WARN 文案已改为指向 `13 §7.4`；这两组方法的实际注册方式仍留待 jadx / 真机 G01 确认（`13 §6 #7`）。

## 10. 路线 A · slot 后期按需实现规程（2026-11-05 拍板）

**术语对齐**：用户所称 **slot** = `11 §6` 原称的 stub / 同名空壳 / 边界占位，三者指同一物。用户决议原话：「**A 后期按需实现 slot**」。

### 10.1 本轮边界（明确不做）

- 不创建 `:engine-legacy` 源码、**不实现任何 slot**、不提取 18 个打包集 so 入库、不生成 `ENGINE-FINGERPRINT`。
- **不预先批量生成 160 个一层边界空壳**（spike #0 原记 168，含 8 个原始类型伪影，见 `11 §9.2`） —— 这正是「按需」的含义，也是避免重演 spike #0 闭包爆炸的关键。
- 不改 `09 §2` 口径；B（dex 片段）不采用。

### 10.2 后期触发与推进顺序

1. 引擎舱开工时（wrapper 已在 §7 #2 就绪）运行 `tools/extract-engine-libs.py --apply --fingerprint-out assets/ENGINE-FINGERPRINT`，把 **18 个打包集 so**（含 `libc++_shared.so`，`13 §2`）落到 `engine-legacy/src/main/jniLibs/arm64-v8a/`。
2. 按 `11 §2.1` 的 4 个 JNI 包族反编译重建 **84 个真类**（jadx / baksmali），包名类名保持竞品原样（JNI 符号硬绑定）。
3. **编译 → 看第一个报错缺哪个类 → 只补那个 slot → 再编译**，循环；编译通过后再跑 G01/G02，运行时暴露的 JNI 回调依赖同样按需补。
4. 每补一个 slot **立即登记**到 §10.4 登记簿，记录触发来源（编译期 / 运行期 / JNI 回调）。
5. ~~顺带用 `11 §3.2` 的 12 个精确类替换 `03-12 §2` 的 R8 keep 示意包名~~ **已提前完成（2026-11-05，`13 §8`）**：落地 `engine-legacy/proguard-rules.pro`（12 精确类 + 4 包族通配 + 媒体会话精确类），C1 升级为「202 个 `Java_*` 符号类全覆盖」FAIL 校验，dev 实测 PASS、WARN 由 5 条降为 4 条。注意这是**静态规则文本**，不违反「不建舱源码 / 不提取 so / 不实现 slot」的边界。

### 10.3 判据与止损

| 项 | 口径 |
|---|---|
| 时间盒 | **2~3 天** |
| 通过 | 84 个真类 + **≤200 个 slot** 能编译出 `IMusicEngine` 实现，且真机 G01/G02（播放 / 暂停）通过 |
